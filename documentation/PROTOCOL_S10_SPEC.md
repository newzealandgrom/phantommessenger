## S10.1 Метаданные внутри E2E — capability `meta1` (X-09, остаток X-03)

**Негоциация.** `register.capabilities` = `["env2", "meta1"]`. Отправитель использует формат meta1, если для собеседника выбран конверт v2 (правило P9) **и** (`lookup_result.capabilities ∋ "meta1"` ИЛИ `peerMeta1[number] == true` — от номера уже приходил meta1-payload; persist вместе с `peerEnv2`, сброс только logout/panic). Иначе — текущий формат (v2 или v1) без изменений.

**Внешний конверт (видит relay)** для всего пользовательского контента — текст, файл, голос, пересылка:
```
{ "type": "message", "toNumber": N, "messageId": "<uuid>", "encryptedBlob": <blob v2> }
```
Никаких `replyTo`, `selfDestruct`, `forwardFrom`, `fileName`, `fileSize`, `mimeType`, `duration` снаружи. Типы `file_message`/`voice_message` meta1-отправитель не использует.

**Plaintext внутри blob v2** = байт `0x00` ‖ UTF-8 JSON-объект (компактный, без BOM):
```
{ "k": "text" | "file" | "voice",
  "text":  string                       // k=text (и подпись к файлу, если есть)
  "data":  base64 std                   // k=file|voice — содержимое (то, что сейчас шифруется в file/voice_message)
  "name":  string, "mime": string, "size": int        // k=file
  "mime":  string, "dur": number                       // k=voice
  "replyTo": {"messageId": string, "from": string}    // опционально
  "fwd":   string                       // опционально, номер исходного автора пересылки
  "sd":    int (секунды) | "read"       // опционально, самоуничтожение
  "pad":   string                       // опционально, игнорируется (паддинг)
}
```
- Маркер `0x00` однозначен: легаси-plaintext (текст пользователя, base64 файла) никогда не начинается с NUL; клиенты вырезают U+0000 из пользовательского текста перед отправкой.
- Получатель: после успешной расшифровки, если первый байт `0x00` → разобрать JSON и диспетчеризовать по `k`; неизвестный `k` → игнор (без пузыря); неизвестные поля → игнор. Иначе — легаси-обработка по внешнему `type`.
- Валидация на приёме: `name` ≤ 255 символов, без управляющих символов и `/ \`; `mime` ≤ 127, вид `type/subtype`; `size`, `dur` — неотрицательные числа в пределах лимитов; `text` ≤ текущего лимита. Нарушение → «[Некорректное сообщение]» без падения.
- Паддинг (SHOULD): отправитель дополняет `pad` пробелами так, чтобы длина plaintext была кратна 256 байтам (если < 4096) или 4096 байтам (иначе), не превышая лимит кадра.
- `message_edit`: внешний тип прежний (`{type:"message_edit", toNumber, messageId, encryptedBlob}`); для meta1-собеседника plaintext = `0x00`‖`{"k":"text","text":…}`.
- **Реакции**: для meta1-собеседника `{type:"reaction", toNumber, messageId:<целевое>, encryptedBlob}`, plaintext = `0x00`‖`{"k":"reaction","emoji":…, "remove":bool}`; снаружи нет `emoji`/`remove`. (Relay видит факт реакции на `messageId`, но не эмодзи.)
- **Остаются открытыми (осознанно, документируется):** `typing` (булево), `read_receipt`/`delivery_receipt` (`messageIds`), `burn_read_ack`, `screenshot_alert`, `message_delete` (`messageIds`), сигналинг звонков/P2P (SDP/ICE — защищены DTLS-SRTP, содержимое SDP — метаданные транспорта). Relay их маршрутизирует; содержимого переписки они не раскрывают.
- **Настройки чата** (`save_chat_settings`: цвет/обои): новые клиенты НЕ отправляют на relay, хранят локально. Relay принимает от старых клиентов, но только в RAM (S10.6).
- **P2P DataChannel**: тот же формат `{type:"message", messageId, encryptedBlob}`; снаружи ничего больше.
- **Mesh-bridge**: без изменений (v1, P8).

## S10.2 Safety number v2 (X-02)
`phantom-safety-v2`:
```
lp(s)  = u8(len(utf8(s))) ‖ utf8(s)
(nLo,kLo),(nHi,kHi) = пары (номер, raw65 identity-ключ) обеих сторон, отсортированные по utf8(номер) (при равенстве номеров — по raw65)
digest = SHA-256( utf8("phantom-safety-v2") ‖ 0x00 ‖ lp(nLo) ‖ kLo ‖ lp(nHi) ‖ kHi )
```
Отображение — как v1: 12 групп по 5 цифр = `uint16BE(digest[2i..2i+1]) % 100000`, i = 0..11, с ведущими нулями.
Номера — те же канонические строки, что `fromNumber`/`toNumber` relay и `from`/`to` в HKDF конверта v2. Ключи — identity-ключи (свой persistent и ключ собеседника из `lookup_result`).
Флаг «проверено» по-прежнему привязан к отпечатку `hex(SHA-256(raw65))[:32]` ключа собеседника (не к строке safety number) — смена формата не сбрасывает проверку.
Эталон: оркестратор генерирует на Python (`documentation/safety_v2_vector.json`); все три клиента обязаны совпасть побайтово.

## S10.3 Блокирующее предупреждение о смене ключа (X-02)
Состояние `keyAlert[number]` (persist вместе с пинами; сброс logout/panic) взводится, когда:
(а) у собеседника, у которого уже был ≥ 1 пин, добавлен новый пин `senderIdentityKey` (новое устройство или смена ключа);
(б) выполняется условие баннера P7 (пины непусты И fp(`lookup_result.publicKey`) ∉ пинам);
(в) снят флаг «проверено» из-за смены ключа.
Пока `keyAlert[number]` взведён — **отправка любого пользовательского контента и исходящий звонок этому собеседнику заблокированы** до явного действия пользователя: модальное/липкое предупреждение «Ключ безопасности собеседника изменился. Сверьте код безопасности или подтвердите, что знаете о смене устройства» с кнопками [Сверить код] и [Продолжить]. «Продолжить» снимает `keyAlert` и запоминает `ackFp[number]` = fp текущего ключа из lookup; повторное срабатывание — только при новом событии (а)–(в) с другим fp. Входящие сообщения продолжают показываться (чтение не блокируется). Первый контакт (пинов нет) — без блокировки.

## S10.4 QR-сверка (X-02)
Содержимое QR: `phantomsafety:2:<свой номер>:<fp своего identity-ключа>:<номер собеседника>:<fp ключа собеседника>` (fp = 32 hex). Сканирующая сторона проверяет, что номера — это (собеседник, я), а оба fp совпадают с её локальными (fp ключа собеседника из lookup и fp своего ключа) → ставит «проверено» (привязка к fp собеседника, как сейчас). Несовпадение → «Коды не совпадают» без изменения флага. Показ QR — все три платформы; сканирование — Android/iOS (камера). Web — только показ + ручная сверка цифр.

## S10.5 Звонки и P2P (X-04)
- **Настройка «Скрывать IP в звонках»** (`privateCalls`, UI в настройках приватности на всех платформах; дефолт: выкл.). Вкл. → `iceTransportPolicy = relay` для звонков.
- **Звонок не от контакта** → всегда `relay` (как в Signal), независимо от настройки.
- **P2P DataChannel** → всегда `relay`. Если TURN недоступен (нет токена/`/api/ice` не дал TURN) — P2P не устанавливается. TURN-креды живут `TURN_CRED_TTL_SEC` (прод 3600 с): P2P-канал пересоздаётся/ICE-restart со свежими кредами до истечения (≥ 5 мин запаса).
- **Фильтр кандидатов** при `all`: не отправлять `typ host` (локальные IP) ни трикл-кандидатами, ни внутри SDP (`a=candidate … typ host`).
- **Входящий `call_offer`**: от номера из локального блок-листа → молча отклонить; до явного «Принять» не создавать PeerConnection, не применять `setRemoteDescription`, не собирать и не отправлять ICE; входящие ICE до принятия — буфер (≤ 64) только от того же номера и `callId`.
- **`callId`**: инициатор генерирует UUID и ставит его во все события звонка; получатель игнорирует `call_answer/ice_candidate/call_hangup/call_reject/call_media_toggle` с другим `callId` (если поле есть у активного звонка).
- **Relay**: лимит частоты `call_offer` и `p2p_offer` на номер-отправитель (`CALL_OFFER_RATE_LIMIT_PER_MIN`, дефолт 10; `P2P_OFFER_RATE_LIMIT_PER_MIN`, дефолт 30); превышение → дроп + `{"type":"error","reason":"rate_limited"}` отправителю. Блок-чек для всех типов сигналинга уже есть (S4/BE-11).

## S10.6 Минимальная персистентность relay и ресинк клиентами (X-06)
- `state.json` содержит **только**: `registered_keys`, `registered_capabilities`, `push_tokens`, `mesh_identities`, `mesh_revocations`. `user_profiles`, `chat_settings`, `blocked_users`, `pinned_messages` — только RAM; при загрузке старого state эти ключи игнорируются (и исчезают с диска при следующем сохранении).
- **Блок-лист — источник правды на клиенте.** Клиент хранит свой блок-лист локально (Android/iOS — в зашифрованном хранилище, web — per-account), после каждого успешного `register` шлёт `{"type":"block_sync","numbers":[…]}` (≤ 1000, нормализованные). Relay: семантика **объединения** (union) с RAM-множеством — никогда не удаляет; удаление только `unblock_user`. Ответ — `blocked_list`. Первый запуск новой версии: если локального списка ещё нет, клиент сначала принимает `blocked_list` от relay (`get_blocked`) как начальный, затем синхронизирует.
- **Профиль.** Клиент хранит свой профиль (`displayName`, `status`, `avatarUrl`) локально и после каждого `register` повторно шлёт `set_profile`, если профиль задан.
- **Пины сообщений**: только RAM на relay; клиенты могут кэшировать локально.

## S10.7 App Lock / Panic — единая модель (X-05)
- PIN и panic-PIN хранятся только как `{v:1, iter, salt(16 B), hash(32 B)}` = PBKDF2-HMAC-SHA256 (iOS — существующие 200 000; web и Android — ≥ 310 000, ≤ ~500 мс на целевом устройстве) в защищённом хранилище (Android — EncryptedSharedPreferences, iOS — Keychain `ThisDeviceOnly`, web — localStorage per-account). Миграция: существующий открытый PIN при первом запуске хэшируется и открытое значение удаляется.
- Сравнение — constant-time; при каждой попытке вычисляются обе проверки (panic и обычный), чтобы время не выдавало наличие panic-PIN. Panic-PIN ≠ обычному (при установке проверять).
- Счётчик неудач — персистентный (в том же защищённом хранилище). Задержки: 1–4 — нет; 5-я — 30 с; 6-я — 1 мин; 7-я — 2 мин; 8-я — 5 мин; 9-я — 15 мин; **10-я неудача → полный wipe** (как panic). UI с 5-й неудачи показывает задержку и «осталось N попыток до удаления данных». Успех обнуляет счётчик.
- Panic-PIN и 10-я неудача → **полный wipe до снятия блокировки**: identity/device-ключи, токены всех аккаунтов, сообщения и кэши, контакты, пины/verified, mesh (ключи, история, комнаты, peer-реестр), prefs, временные файлы; после — экран входа, без признаков panic (без логов «panic» в системных журналах).
- Пока заблокировано — чувствительный контент не рендерится/не компонуется под оверлеем (Android — не композить контент; iOS — оверлей в отдельном `UIWindow` над модалками, повторная блокировка по `scenePhase`/background с учётом таймаута; web — не рендерить приложение, только экран блокировки). Уведомления при включённой блокировке — без текста.
- Тест на каждой платформе: хэш/проверка/миграция/счётчик/задержка/wipe-порог (Android — JUnit; web — node-скрипт над чистыми функциями; iOS — swift-скрипт как `scratchpad/ios-dev/envelope_v2_test.swift`).

## S10-ПРАВКИ (после ревью архитектора 2026-10-12 — ОБЯЗАТЕЛЬНЫ, имеют приоритет над текстом выше)

Факты из кода, на которых основаны правки: file/voice на всех платформах шифруют строку `base64(bytes)` (web `App.tsx:2854, 3023`; Android `ChatViewModel.kt:1489-1493, 1675-1679`; iOS `ChatView.swift:1851-1858, 1924-1931`); WS-кадр relay ≤ 256 KiB для любого типа (`main.py:2550, 2849`), офлайн-очередь ≤ 1 MiB на сообщение; HTTP `/api/messages/send` без капа размера; push-текст выбирается по `payload["type"]` (`main.py:1060-1079`); `duration` легаси: web/iOS — секунды, Android — мс; `callId` сейчас не шлёт никто; ни один клиент не хранит блок-лист локально (`get_blocked` при коннекте); профиль Android живёт только на relay; relay `reaction` собирает фиксированный dict и выбрасывает лишние поля (`main.py:3201-3222`).

### Q1. Единый диспетчер meta1
file/voice/text meta1-отправителя → внешний `type:"message"`. Приёмники `file_message`/`voice_message` (легаси) сохраняются бессрочно. После расшифровки — ОДНА функция-диспетчер на платформу, вызываемая из `message`, `message_edited`, `reaction`, P2P DataChannel и HTTP-poll.

### Q2. Длительность голоса
В meta1 — `durMs: int` (миллисекунды). Поле `dur` из черновика не используется. Легаси `duration` на приёме: значение `< 1000` трактуется как секунды, иначе как миллисекунды.

### Q3. Согласованность `k` ↔ внешний тип (защита от перестановки контекста relay'ем)
`message` ⇒ `k ∈ {text, file, voice}`; `message_edited` (вход) / `message_edit` (выход) ⇒ `k = text`; `reaction` ⇒ `k = reaction`. Иначе — дроп без пузыря.

### Q4. Привязка к внешнему `messageId`
Для `k ∈ {text, file, voice}` обязательное поле `id` = внешний `messageId` (для правки — id правимого сообщения). `id ≠ messageId` → дроп. Для `k = reaction` — обязательное `target` = внешний `messageId` (целевое сообщение) и `emoji` (≤ 32 UTF-16 code units — единая единица на всех клиентах: web `.length`, Android `String.length`, iOS `utf16.count`; запрещены Cc и bidi-управляющие U+200E/U+200F/U+202A–U+202E/U+2066–U+2069; ZWJ U+200D, вариационные селекторы U+FE0E/U+FE0F и теги U+E0020–U+E007F РАЗРЕШЕНЫ — составные эмодзи вроде ❤️‍🔥), `remove: bool`.

### Q5. Явные лимиты
`text` ≤ 16 384 символов; `name` ≤ 255 символов и без символов Unicode-категорий Cc, Cf (в т.ч. bidi U+200E/U+200F/U+202A–U+202E/U+2066–U+2069), Co, Cn, Zl, Zp и без `/` `\` (нарушение → «[Некорректное сообщение]», отправитель такие символы вырезает); `mime` — только ASCII `^[\w.+-]+/[\w.+-]+$` ≤ 127; весь внешний кадр ≤ `MESSAGE_MAX_BLOB_BYTES` = 262 144 байт (кап WS-кадра relay не меняем). Клиенты считают максимальный размер файла от капа (140 КиБ исходных байт: содержимое кодируется base64 дважды — `data` внутри plaintext и `cipher` снаружи; web и iOS считают так же) и честно показывают лимит вместо «10 МБ». Relay применяет тот же кап к HTTP `/api/messages/send`, `message_edit`, `forward`.

### Q6. Тест-векторы meta1
Сравниваются РАСШИФРОВАННЫЕ байты plaintext и разобранные поля, не `cipher` (сериализация JSON у платформ различна). Эталон: `documentation/meta1_vector.json` (ключи/номера/AD из `protocol_v2_vector.json`), включая негативы: без NUL (легаси), неизвестный `k`, `id ≠ messageId`, `k` ↔ тип, некорректное `name`.

### Q7. Блокировка отправки (S10.3) — только (а) и (в)
Блокировать при (а) новый пин при уже непустом множестве пинов и (в) снятии verified из-за смены ключа. Условие (б) (ключ с relay ∉ пинам, P7) — липкий НЕблокирующий баннер с запретом ставить verified, как сейчас. Не взводить, если новый fp ∈ `ackFp[number]` или = `lastVerifiedIdentity`. Гейт — одна функция `canSendTo(number)` на платформу, применяется к relay, HTTP-фоллбэку, P2P и исходящему звонку; receipts/typing не блокируются; исключения: `from == self`, «Избранное»/Saved, `_meshBridge`.

### Q8. Версия safety number по capability
Если `lookup_result.capabilities ∋ "meta1"` для собеседника — показывать safety v2 и QR v2, иначе v1 (обе стороны сходятся детерминированно). Capability `meta1` означает «клиент S10» целиком: meta1 + safety v2 + QR v2 + `block_sync`. Документировать: в мульти-девайсе safety number зависит от primary-устройства собеседника.

### Q9. Звонки и P2P (решение оркестратора по S10.5)
- `privateCalls` (UI «Скрывать IP в звонках»), дефолт выкл.; звонок не от контакта — всегда `relay`.
- **Автоматический P2P — только по согласию:** новая настройка `p2pFallback` (UI «Резервный P2P-канал при недоступности сервера», пояснение «собеседник увидит ваш IP-адрес, если не включено „Скрывать IP“»), **дефолт выкл.** При выкл. клиент не шлёт `p2p_offer` и игнорирует входящие `p2p_offer`. При вкл. — гейт S4 + политика ICE как у звонков (`privateCalls` → `relay`, иначе `all` с фильтром host).
- При `all` — не отправлять кандидаты `typ host` (и `prflx` в P2P web `App.tsx:3333`), ни трикл, ни в SDP.
- ICE-серверы кэшируются с `expiresAt` (TTL из `/api/ice`) и перезапрашиваются перед каждым новым PeerConnection; при `relay` для долгоживущего P2P — ICE-restart/пересоздание за ≥ 5 мин до истечения.
- Отклонение от report P1 #15 («relay по умолчанию для P2P») записывается: вместо relay-only P2P выключен по умолчанию (сильнее по приватности; P2P через TURN бесполезен при падении relay — креды не обновить, TTL 3600 с).

### Q10. `callId`
Инициатор генерирует UUID и ставит `callId` во все события звонка. Получатель при наличии `callId` у активного звонка игнорирует события с другим `callId`; при отсутствии — поведение S4 (по номеру). Relay: `callId` строка ≤ 64 символа, иначе поле вырезается.

### Q11. Блок-лист: `block_sync` с tombstone, персистентность под флагом
`{"type":"block_sync","numbers":[…],"unblocked":[…]}` (каждый список ≤ 1000, нормализованные номера). Relay: `set |= numbers; set -= unblocked`, ответ `blocked_list`. Клиент хранит блок-лист локально (Android/iOS — зашифрованное хранилище, web — per-account localStorage) и tombstones `unblockedAt` 30 дней; шлёт `block_sync` после каждого успешного `register`. Первый запуск новой версии без локального списка: сначала `get_blocked` → принять как начальный, потом синхронизировать. Персистентность `blocked_users` на relay — под флагом `PERSIST_BLOCKED_USERS` (дефолт 1) до релиза мобильных с `block_sync`; затем владелец ставит 0. `user_profiles`, `chat_settings`, `pinned_messages` — RAM-only сразу; `_load_state` их игнорирует.

### Q11a. Профиль
Клиент хранит свой профиль (`displayName`, `status`, `avatarUrl`) локально и после каждого `register` шлёт `set_profile`, если профиль задан (web профиля не имеет — ничего не делает).

### Q12. Мульти-девайс
`message_sync` на другие устройства отправителя содержит blob, зашифрованный на ключ собеседника — собственные устройства его не читают (так и в v1/v2). Известное ограничение «мульти-девайс без синхронизации содержимого».

### Q13. Web-блокировка
Не размонтировать приложение (иначе рвётся WS): оверлей блокировки поверх, корень приложения `inert` + `visibility:hidden`/`aria-hidden`, уведомления без текста. Честно: plaintext остаётся в памяти вкладки; счётчик неудач в localStorage обнуляем тем, у кого есть доступ к профилю браузера.

### Q14. Счётчик и wipe
`failCount` и `lockedUntil` персистентны и переживают перезапуск. Wipe на web обязан дойти до Service Worker (IndexedDB `phantom-keystore`) отдельным сообщением `wipe`, иначе identity-ключ выживет.

### Q15. Санитизация легаси на relay
Для `file_message`/`voice_message` от старых клиентов: `fileName` ≤ 255 без управляющих символов и `/ \`, `fileSize` int 0…кап, `mimeType` по regex `^[\w.+-]+/[\w.+-]+$` ≤ 127, `duration` число ≥ 0; `encryptedBlob` обязателен (иначе ошибка `invalid_blob`). `reaction`: passthrough `encryptedBlob` (если есть); `emoji` ≤ 16 символов.

### Q16. Даунгрейд meta1 → легаси
`peerMeta1[number]` липкий (persist рядом с `peerEnv2`, сброс только logout/panic). Входящее легаси-формата (без NUL) от номера с `peerMeta1` → показать + однократное за сессию системное «Метаданные этого сообщения пришли по старому формату (возможно, с другого устройства собеседника)».

### Q17. Ошибка лимита
`{"type":"error","reason":"rate_limited"}` — клиенты обязаны молча (или тостом) терпеть неизвестные `reason`, без модалок и без разрыва WS.

### Q18. Mesh-bridge
Через bridge — только текст (v1, P8); файлы/голос через bridge не поддерживаются — записать явно.

### Внеплановые wire-баги iOS (блокирующие, исправить в том же релизе)
`Models.swift:259-262` шлёт `pinMessage`/`unpinMessage` вместо `pin_message`/`unpin_message` (пины iOS не доходят); `forward` (`Models.swift:273-278`) шлёт `originalMessageId` без `forwardFrom`/`messageId`; для QR-сканера — `NSCameraUsageDescription` в Info.plist.

### Q19. Единая семантика валидации meta1 (после крипто-ревью, обязательна для всех трёх клиентов)
- `sd`: допустимо целое 1…604 800 (7 сут) или строка `"read"`; иное значение → поле игнорируется (сообщение показывается без таймера), пузырь НЕ помечается некорректным.
- `k = file`: `name`, `mime`, `size` обязательны (иначе «[Некорректное сообщение]»); `k = voice`: `mime`, `durMs` обязательны; `durMs` ≤ 3 600 000.
- `k = voice`, поле `wave` (необязательное, голосовые v2): base64 ровно 63 байта, иначе поле игнорируется без пометки «некорректно»; формат файла, волна и эталон — `documentation/PROTOCOL_VOICE_V2.md`, `documentation/voice_v2_vector.json`.
- `k = reaction`: `target`, `emoji`, `remove` (bool) обязательны; отсутствие `remove` → дроп.
- `peerMeta1[number]` выставляется при ЛЮБОМ NUL-payload, прошедшем GCM (включая последующие drop/invalid).
- Легаси-обработчики `file_message`/`voice_message`: если расшифрованный plaintext начинается с `0x00` → дроп без пузыря (Q3: meta1-payload во внешнем легаси-типе — перестановка контекста).

## M-ПРАВКИ (mesh X-07, обязательны)
- **M1.** «Адресный» пакет = `recipient ≠ 0x00×16` и `recipient ∉ наши roomRecipientId` (оба id комнаты — с паролем и без). `encrypted` (Noise) обязателен для адресных TEXT, VOICE, PHOTO, PHOTO_FULL, SCREENSHOT_ALERT, REACTION, LIVE_AUDIO_CHUNK. **TYPING — подписанный plaintext, требуется только `verified`** (финальное решение после ревью: Noise-транспорт с неявным последовательным nonce не допускает переупорядочивания, а TYPING обгонял фрагменты медиа и навсегда рассинхронизировал DM-сессию; содержимого у TYPING нет, подлинность даёт подпись). При ошибке расшифровки при существующей сессии получатель шлёт REKEY_HINT (verified, ≥ 30 с на пира). Комнатные LIVE/CHANNEL/REACTION — только `verified`.
- **M2.** Отказ без `FLAG_SIGNED`/подписи — до dedup, для ВСЕХ типов, включая NOISE_* и STORE_FORWARD_*. Проверить, что ретрансляция (TTL-flood, store-forward, BRIDGE_FORWARD) не пересобирает подписанные поля.
- **M3.** Noise-handshake от id, ещё не известного реестру: не отвергать навсегда — pending ≤ 10 с, завершать после прихода проверенного PEER_ANNOUNCE и только если remote static == `static_pub` из реестра; иначе отказ.
- **M4.** PeerRegistry никогда не перезаписывает ключи известного id (конфликт → отклонить, событие для UI). Подтвердить, что anon-id и NFT-id выводятся из `signing_pub`; если для домена id проверяем без номера — проверять деривацию при TOFU. Легитимная ротация — только через MESH_KEY_REVOCATION (S7) → запись удаляется, следующий анонс = новый TOFU + событие UI.
- **M5.** REKEY_HINT — только verified, троттлинг ≥ 30 с на peer; `inst`-эвикция — только verified и только при реальной смене `inst`.
- **M6.** Негативные/fuzz-тесты декодера пакетов на усечённых буферах (JVM + swift-скрипт); Android `BufferUnderflowException` и iOS выход за диапазон `subdata` → дроп пакета, не краш.
- **M7.** Прямые `android.util.Log.*` в mesh (`MeshRuntime.kt:914` и др.) — убираются proguard-правилом release (шаг Android chat); убедиться, что release собирается с `isMinifyEnabled=true`.
- **M8.** Mesh-история и комнаты — RAM по умолчанию; opt-in «Сохранять историю mesh на устройстве» (зашифровано, как сейчас); выключение стирает файлы истории/комнат. Пароли комнат живут в Keystore/Keychain, стираются при logout/panic. Peer-реестр (пины ключей) остаётся зашифрованным персистентным — это состояние безопасности.

## Остаётся открытым осознанно (записать в SECURITY_AUDIT.md)
Relay видит факт/время/размер-бакет сообщений, `messageId` реакций, `messageIds` receipts/delete, typing, SDP/ICE, кто кому пишет; forward secrecy только у отправителя (компрометация identity-ключа получателя раскрывает всё адресованное ему); мульти-девайс без синхронизации содержимого; web — SW/IndexedDB не граница доверия, блокировка обходится доступом к профилю браузера; mesh — id не самоудостоверяющий (гонка TOFU первого анонса), комнаты не шифруются (пароль скрывает только recipient-id), attestation в announce не передаётся (MESH-07); «зомби-блок» после долгого офлайна смягчён tombstones; P2P при упавшем relay — только с ранее полученными TURN-кредами; coturn/Cloudflare/nginx видят IP.
